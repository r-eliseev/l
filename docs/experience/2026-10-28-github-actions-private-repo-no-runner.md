# Actions в приватном репозитории падает без раннера — это не ошибка workflow

## Ситуация

GitHub Actions в приватном репозитории владельца (`r-eliseev/ddd-praktika`).
Джобы завершаются `failure` за 3–4 секунды, не выполнив ни одного шага:
в API у job пустые `steps`, пустой `runner_name`, пустые `labels`.

Тот же период: публичный репозиторий владельца работает нормально, приватные
падают.

## Что сработало или не сработало

Не сработало: предположение, что виноват YAML. Файл действительно вызывал
подозрения — `on: pull_request:` с пустым значением рядом с `push:` —
поэтому первым делом проверили разметку (валидна) и стали искать в логах.

Логи не читались: `gh run view --log` отдавал «log not found», прямой запрос
к API логов — `BlobNotFound`. Причина в том, что прогон не дошёл до шагов:
логи просто не создавались.

Сработало: пробный workflow из одной строки `echo "probe ok"`, запушенный
в том же репозитории. Он упал точно так же — ноль шагов, нет раннера. Это
исключило наш конфиг: если бы дело было в YAML, пробный workflow с тремя
строками отработал бы.

Второе, что помогло: сравнение с другими репозиториями того же аккаунта.
У публичного `studious-goggles` — 91 успешный прогон из 100, последний
успешный сегодня в 20:12 UTC. У приватного `refactored-doodle` последний
успешный — 11 июля, дальше только падения. Значит, дело в аккаунте и
приватности репозитория, а не в конкретном проекте.

Вывод: у аккаунта исчерпан лимит минут Actions для приватных репозиториев
(или он выставлен в ноль). Это настройка аккаунта, а не репозитория:
Settings → Billing and licensing → Budgets and alerts → Actions.

## Доказательства

- Пробный workflow `probe.yml` (одна задача, `runs-on: ubuntu-latest`,
  шаг `run: echo "probe ok"`) → job `probe`: `failure`, `runner_name: ''`,
  `steps: 0`, `started_at` 20:11:16 → `completed_at` 20:11:20.
- То же для джобов `check` и `book` основного workflow.
- `gh run list -R r-eliseev/studious-goggles --limit 100 --json conclusion`:
  91 успешных, последний успешный 2026-10-28T20:12:33Z (публичный репозиторий,
  тот же аккаунт, тот же момент времени).
- `gh run list -R r-eliseev/refactored-doodle --limit 100 --json conclusion`:
  последний успешный 2026-07-11 (приватный репозиторий).
- YAML проверен `yaml.safe_load` — оба workflow файла разбираются без ошибок.
- Локальная имитация обоих джобов (`BASE_REF=origin/main bash scripts/check.sh`
  и последовательность `unittest` → `lint_book.py` → `check_quotes.py` →
  `build_epub.py` → `validate_epub.py`) — все шаги завершаются с кодом 0.

## Итог

Позже (2026-10-28) репозиторий перевели в публичный режим и переименовали
в `l`. Actions заработали сразу: прогон 40840352057 — все четыре джоба
зелёные, включая сборку и валидацию EPUB обеих книг. Значит, дело было не в
workflow, а в настройке аккаунта для приватных репозиториев (лимит минут
или трат).

Вывод не изменился: сначала пробный workflow, потом сравнение с другими
репозиториями аккаунта. Просто приватность — это первое, что стоит
проверять, когда джобы падают без раннера.

## Что делать в следующий раз

Не чинить workflow, пока не проверен пробный: одношаговый workflow с
`echo` отделяет «наша конфигурация сломана» от «среда не даёт раннер» за один
push. Дальше — сравнить с другими репозиториями того же аккаунта (публичный
против приватного): это разделяет проблему аккаунта и проблему проекта.

Пока Actions для приватных репозиториев не работают, держать проверки
исполняемыми локально: те же команды, что в CI, должны запускаться руками
без правок.
