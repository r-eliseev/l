# Модуль 10. Fargate

Этот модуль почти целиком про EKS. В обычном Kubernetes нет готового
аналога. Есть похожая идея (проект Virtual Kubelet), но в EKS она встроена и
поддерживается AWS. Понятие «нода», которую вы видите и администрируете,
фактически исчезает.

## Общее (на уровне API)

Общим остаётся верхний уровень:

- Pod, Deployment, Service описываются точно так же;
- приложению всё равно, где оно физически исполняется.

```bash
kubectl apply -f deployment.yaml   # манифест не отличается от обычного
```

Поэтому для приложения Fargate прозрачен: разница на уровне платформы, а не
API.

## В EKS: что меняется принципиально

- **У каждого пода своя микро-VM и своя «нода».** Поды не делят ядро, CPU,
  память и сетевой интерфейс.[28] `kubectl get nodes` покажет «fargate-ноды», но
  это по одной на под, а не физическая машина с множеством подов.
- **Fargate Profile** — объект, которого нет в обычном Kubernetes. Это
  правило: какие поды (по namespace и labels) уходят на Fargate, а какие на
  обычные ноды. Под, который не подошёл ни под один профиль, на Fargate не
  попадёт, а при нехватке других нод зависнет в `Pending`.

```bash
aws eks create-fargate-profile \
  --cluster-name my-cluster \
  --fargate-profile-name batch \
  --pod-execution-role-arn arn:aws:iam::123456789012:role/FargatePodExecutionRole \
  --subnets subnet-aaa subnet-bbb \
  --selectors namespace=batch-jobs
```

- **Только приватные подсети.** Поды Fargate запускаются в частных подсетях
  (с выходом в интернет через NAT gateway либо через VPC endpoints).[28] В
  публичной подсети Fargate-под не запустится.
- **DaemonSet не работает.** Самая частая неожиданность при переходе с
  EC2-нод.[28] DaemonSet — это «по одной копии на каждую ноду», а общих нод на
  Fargate нет. Агент логов или мониторинга приходится делать sidecar-контейнером
  внутри каждого пода. Для логов есть встроенный log router (модуль 08).
- **Ограничения среды:**
  - нет `hostNetwork` и `hostPort`[28];
  - нет privileged-контейнеров;
  - нет GPU[28];
  - только Linux на x86_64 (ARM и Windows не поддерживаются);
  - нет Spot[28];
  - нет доступа к instance metadata service (IMDS): регион и зону нужно
    передавать в под явно;
  - нельзя использовать альтернативный CNI: на Fargate работает только VPC
    CNI;
  - размеры только из таблицы допустимых пар vCPU и памяти, размер считается
    по requests подов (с небольшим запасом на системные компоненты) и
    округляется вверх.
- **Хранилище.** EBS подключить нельзя[28]. EFS можно, но **только со статическим
  PV**: динамическое создание томов на Fargate не поддерживается. Драйвер
  вручную ставить не нужно, Fargate монтирует EFS сам.[29]
- **IAM для подов.** IRSA работает. **Pod Identity не поддерживается**
  (модуль 04).
- **Балансировщики.** Только `target-type: ip` (модуль 05).
- **Security groups для отдельных подов** на Fargate можно.
- **Деньги.** Платите за vCPU и память, запрошенные подом, с округлением до
  допустимой конфигурации, от начала загрузки образа до остановки пода,
  минимум минута. Пустой «простаивающей ноды» нет, но и уплотнить много
  мелких подов на одну дешёвую ноду нельзя. Завершённые Job остаются
  подами: задайте `ttlSecondsAfterFinished`[28], иначе будете платить за
  хранение завершённых подов.
- **Обновления.** Поды Fargate не обновляются сами вместе с control plane.
  Чтобы получить свежий kubelet, под нужно пересоздать (rolling restart).
  AWS периодически патчит нижний слой и при этом выселяет поды, так что
  нужны реплики и PDB.
- **Автоскейлинг нод не нужен.** Cluster Autoscaler и Karpenter для
  Fargate-подов теряют смысл (модуль 06). HPA работает.
- **CoreDNS.** Если в кластере нет EC2-нод и CoreDNS должен жить на Fargate,
  его нужно перенастроить: по умолчанию он ждёт EC2. Eksctl делает это
  автоматически, при ручной настройке придётся убрать аннотацию
  `eks.amazonaws.com/compute-type: ec2` у деплоймента CoreDNS и перезапустить
  его.

## Практика на kind

Честно: **воспроизвести Fargate на kind нельзя.** Это главный вывод модуля.
Что можно сделать вместо этого:

1. Разобрать по манифестам, какие нагрузки из предыдущих модулей не
   поедут на Fargate: DaemonSet с node-exporter (модуль 08), поды с PVC на EBS
   (модуль 03), поды с Pod Identity (модуль 04).
2. Написать Fargate Profile для гипотетического кластера: например, весь
   namespace `batch-jobs` едет на Fargate, а `monitoring` с DaemonSet остаётся
   на EC2-нодах.
3. Посчитать на бумаге, что дешевле для одного и того же набора подов:
   Fargate или managed node group (цены берите с актуальной страницы AWS).

## Частые ошибки

- Профиль есть, но поды в `Pending`: namespace или labels не совпали, либо
  нет приватных подсетей.
- DaemonSet создан, но «ничего не происходит».
- Pod Identity на Fargate: роль не подтягивается.
- Забыть про TTL у Job и платить за завершённые поды.

## Проверка себя

- Почему DaemonSet для сбора логов не работает на Fargate и что используют
  вместо него? *(Нет общей ноды, на которой он размещает по копии.
  Используют sidecar или встроенный log router.)*
- Какое хранилище доступно на Fargate? *(EFS, только статические PV. EBS
  недоступен.)*
- Какой механизм IAM для подов не работает на Fargate? *(Pod Identity;
  используйте IRSA.)*
