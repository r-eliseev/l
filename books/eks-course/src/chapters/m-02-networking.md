# Модуль 02. Сеть и CNI

(В исходной версии курса этого модуля не было, хотя на него ссылались
остальные.)

## Общее

Модель сети Kubernetes одна для всех:

- у каждого пода свой IP-адрес;
- любой под может обратиться к любому другому по IP без NAT;
- Service даёт стабильный виртуальный адрес поверх набора подов;
- внутри кластера есть DNS (CoreDNS): `имя.namespace.svc.cluster.local`.

Как именно это реализовано, решает **CNI-плагин**. Это главное, где kind и EKS
расходятся.

### Практика на kind

В kind по умолчанию работает простой плагин kindnet. Поды получают адреса из
своей сети, не связанной с вашей «настоящей» сетью.

```bash
kubectl create deployment web --image=nginx --replicas=2
kubectl expose deployment web --port=80
kubectl get pods -o wide                        # у подов свои IP
kubectl run tmp --rm -it --image=busybox -- sh  # дальше внутри пода:
#   nslookup web
#   wget -qO- http://web
```

**NetworkPolicy.** Это правила «кто с кем может говорить». Они работают
только если CNI их умеет. Простой способ попрактиковаться: создать кластер
без встроенного CNI и поставить Calico или Cilium.

```yaml
# kind-calico.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  disableDefaultCNI: true
  podSubnet: 192.168.0.0/16
nodes:
  - role: control-plane
  - role: worker
```

Манифест Calico берите из его актуальной инструкции (версия меняется). Потом
проверьте политику «запретить всё»:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny }
spec:
  podSelector: {}
  policyTypes: [Ingress]
```

После неё `wget http://web` из другого пода должен зависнуть.

## В EKS

### VPC CNI: у подов настоящие адреса VPC

В EKS по умолчанию стоит **Amazon VPC CNI** (DaemonSet `aws-node` в
`kube-system`). Он даёт каждому поду **реальный IP-адрес из вашей VPC-подсети**.
Из этого следует многое:

- Под видно из остальной сети VPC без NAT и туннелей: из EC2, RDS, через
  peering или VPN. Security groups и VPC Flow Logs работают на уровне этих IP.
- ALB может слать трафик прямо в под (`target-type: ip`, модуль 05).
- **Адресов может не хватить.** Каждый под занимает адрес из подсети. Маленькие
  подсети (например /24) быстро кончаются. Это одна из самых частых проблем
  в EKS.

### Сколько подов помещается на ноду

Плагин берёт IP-адреса через сетевые интерфейсы (ENI) инстанса. У каждого типа
EC2 свой лимит интерфейсов и адресов на интерфейс. По умолчанию:

```
макс. подов = ENI × (IP на ENI − 1) + 2
```

Для `m5.large` (3 ENI, 10 IP на ENI) это 3 × 9 + 2 = **29 подов**. В kind такого
ограничения нет: там лимит обычный, около 110 подов.

Посмотреть лимиты типа инстанса:

```bash
aws ec2 describe-instance-types --instance-types m5.large \
  --query "InstanceTypes[].NetworkInfo.[MaximumNetworkInterfaces,Ipv4AddressesPerInterface]"
```

### Как увеличить число подов и сэкономить адреса

- **Prefix delegation** (`ENABLE_PREFIX_DELEGATION=true`). Вместо отдельных IP
  интерфейсу выдаются блоки по 16 адресов (/28). Подов на ноду становится
  намного больше. Нужны Nitro-инстансы и достаточно свободных непрерывных
  блоков в подсети, иначе будет ошибка `InsufficientCidrBlocks`. Лимит подов
  при этом нужно явно передать kubelet (`max-pods`), иначе действует старая
  формула.
- **Custom networking.** Поды берут адреса из отдельных подсетей (например,
  из дополнительного CIDR VPC), а не из тех, где стоят ноды.
- **IPv6-кластер.** Поды получают IPv6-адреса, проблема нехватки IPv4 уходит.
- **Security groups для подов.** Отдельная security group на конкретный под
  вместо одной на всю ноду.

### NetworkPolicy в EKS

VPC CNI умеет NetworkPolicy сам (через eBPF), но функцию надо включить:
в настройках add-on `vpc-cni` значение `{"enableNetworkPolicy": "true"}`.
Требуется ядро Linux 5.10 и выше (в актуальных EKS-оптимизированных AMI оно
есть). По умолчанию (режим standard) новый под сначала открыт, пока к нему не
применятся политики. Режим strict закрывает всё до применения политик.
Вместо этого можно поставить Calico или Cilium. Но на Fargate альтернативный
CNI использовать нельзя.

### Что остаётся общим

CoreDNS и kube-proxy работают как обычно (в EKS они ставятся как add-ons,
модуль 07). Service CIDR (адреса сервисов) задаётся при создании кластера и
**потом не меняется**, поэтому выбирайте его заранее так, чтобы он не
пересекался с вашими сетями.

## Частые ошибки

- Берут для нод маленькие подсети. Поды зависают в `ContainerCreating` с
  ошибкой про нехватку IP.
- Включают prefix delegation, но не меняют `max-pods`. Выигрыша нет.
- Ждут, что NetworkPolicy заработает «сама». Её нужно включить в CNI.

## Проверка себя

- Почему под в EKS можно пингануть из EC2-машины в той же VPC, а под в kind
  из вашей машины нельзя? *(У пода реальный IP VPC; в kind IP принадлежит
  внутренней сети Docker/CNI.)*
- Сколько подов поместится на `m5.large` без prefix delegation? *(29.)*
- Почему маленькая подсеть — риск для EKS? *(Каждый под занимает реальный
  IP из подсети.)*
