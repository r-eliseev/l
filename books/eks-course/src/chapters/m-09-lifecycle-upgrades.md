# Модуль 09. Жизненный цикл и обновления

## Общее

Версии Kubernetes выходят примерно раз в четыре месяца. Правила совместимости
версий (skew policy):

- **kubelet** на нодах может быть **старше** API server не более чем на три
  минорные версии и не может быть новее его;
- **kubectl** может отличаться от API server не более чем на одну минорную
  версию;
- обновлять кластер нужно **по одной минорной версии за раз**.

```bash
kubectl version
```

### Практика на kind

kind не умеет обновлять кластер на месте. Обновление означает создать
кластер заново с другим образом ноды (тег образа берите из заметок к релизу
kind):

```bash
kind create cluster --name old --image kindest/node:<версия-из-release-notes>
```

Зато на kind удобно отработать самое важное для обновлений: **PodDisruptionBudget
(PDB)** и **drain**.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: nginx-pdb }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: nginx } }
```

```bash
kubectl create deployment nginx --image=nginx --replicas=3
kubectl apply -f pdb.yaml
kubectl drain eks-lab-worker --ignore-daemonsets --delete-emptydir-data
```

Если на ноде стоят поды, выселение которых нарушило бы PDB, drain будет
ждать и повторять попытки. Именно это происходит при обновлении нод в EKS.

## В EKS

- **Обновление control plane** делает AWS, одной командой или кликом. По
  одной минорной версии за раз. После обновления в течение 7 дней можно
  откатиться на предыдущую минорную версию (для кластеров, обновлённых
  вручную; автоматически обновлённые откатить нельзя).

```bash
aws eks update-cluster-version --name my-cluster --kubernetes-version 1.36
aws eks list-insights --cluster-name my-cluster   # проверки готовности к обновлению
```

  Перед обновлением загляните в **upgrade insights**: они предупреждают, что
  в кластере используются API, которые исчезнут в новой версии.
- **Рекомендуемый порядок:** control plane, затем add-ons (модуль 07), затем
  ноды.
- **Ноды не обновляются сами**, ни managed, ни self-managed. Если ноды
  отстали от control plane больше чем на три минорные версии, вы вышли за
  пределы совместимости.
- **Managed node group** обновляется через AWS:

```bash
aws eks update-nodegroup-version --cluster-name my-cluster --nodegroup-name workers
```

  Как это происходит: создаются новые ноды (с запасом), старые помечаются
  непланируемыми, поды выселяются (drain) с учётом PDB, затем старые ноды
  удаляются. За раз обновляется не больше `maxUnavailable` нод (по умолчанию
  **одна**, максимум 100). Если поды не ушли с ноды за 15 минут, обновление
  падает с ошибкой `PodEvictionFailure`, если не указать `--force`
  (тогда поды будут удалены принудительно).
- **PDB здесь работает в обе стороны.** Без PDB, если все реплики сервиса
  оказались на одной ноде, их выселят разом, и будет простой. Слишком
  строгий PDB (например, `minAvailable` равен числу реплик) блокирует
  выселение, и обновление упирается в 15 минут и падает.
- **Self-managed nodes:** вы сами создаёте новую группу с новым AMI и сами
  делаете drain. Это ближе всего к kubeadm.
- **Fargate:** поды не обновляются автоматически. Чтобы получить нужную
  версию kubelet, поды нужно пересоздать (rolling restart).
- **Auto Mode:** ноды живут не дольше 21 дня и заменяются автоматически,
  с учётом PDB (модуль 11).
- **Поддержка версий.** Версия получает стандартную поддержку 14 месяцев,
  затем 12 месяцев extended support за дополнительную плату ($0.60 вместо
  $0.10 в час за кластер). После этого control plane принудительно
  обновляется. На октябрь 2026: стандартная поддержка — 1.34–1.37,
  extended — 1.31–1.33. Свежие даты: `aws eks describe-cluster-versions`.
- **Объекты API.** Устаревшие версии API выводятся по расписанию апстрима.
  EKS повторяет его, так что манифесты надо поддерживать актуальными.

## Частые ошибки

- Обновить control plane, а ноды и add-ons оставить на месяцы.
- Нет PDB, и обновление нод роняет сервис.
- PDB слишком жёсткий, и обновление нод зависает на выселении.
- Все реплики одного сервиса на одной ноде: нет `topologySpreadConstraints`
  или anti-affinity.

## Проверка себя

- Зачем нужен PDB при обновлении managed node group? *(Он не даёт выселить
  слишком много реплик одновременно. Но и слишком строгий PDB блокирует
  обновление.)*
- Сколько нод по умолчанию обновляется одновременно? *(Одна.)*
- Что произойдёт, если версия вышла из extended support? *(Control plane
  будет автоматически обновлён, ноды останутся на старой версии.)*
