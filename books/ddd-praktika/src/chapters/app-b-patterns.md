# Приложение Б. Паттерны DDD кратко

*Шпаргалка на одну страницу. Подробности — в соответствующих главах.*

## Стратегические паттерны

| Паттерн | Суть | Когда применять |
|---|---|---|
| Bounded Context | Граница, внутри которой одна модель | Всегда; это базовый элемент |
| Ubiquitous Language | Общий язык модели и кода | Всегда |
| Core Domain | Часть домена с конкурентным преимуществом | Когда решаете, куда вложить усилия |
| Subdomain | Часть домена: core, supporting, generic | При разборе большого домена |
| Context Map | Связи между контекстами | Когда контекстов больше одного |
| Anti-Corruption Layer | Переводчик чужой модели | При интеграции с чужой или legacy-системой |
| Shared Kernel | Общая часть модели и кода | Когда команды тесно связаны и готовы к общему ритму |
| Conformist | Принять чужую модель как есть | Когда перевод дороже, чем подчинение |
| Published Language | Общий формат обмена | Когда контексты обмениваются данными |
| Separate Ways | Не интегрировать вовсе | Когда связь не нужна |
| Partnership | Совместная разработка интеграции | Когда провал одного контекста означает провал другого |
| Customer/Supplier | Явные отношения и планирование | Когда upstream зависит от требований downstream |
| Open-host Service | Открытый протокол интеграции | Когда интегрируются многие |
| Big Ball of Mud | Запутанная зона без границ | Диагностика: что не так |

## Тактические паттерны

| Паттерн | Суть | Признак в коде |
|---|---|---|
| Entity | Объект с устойчивой идентичностью | Есть id, `__eq__` сравнивает по нему |
| Value Object | Объект без идентичности, неизменяемый | `frozen=True`, сравнение по значению |
| Aggregate | Граница согласованности с корнем | Один корень, наружу — только ссылки на него |
| Repository | Доступ к агрегатам как к коллекции | `get`, `add`, `update`, поиск по критериям |
| Domain Event | Факт, важный для экспертов домена | Неизменяемый, с временем и идентификаторами |
| Domain Service | Процесс, не принадлежащий ни одной сущности | Отдельный интерфейс, имя из единого языка |
| Specification | Переиспользуемое правило-предикат | `is_satisfied_by(x) -> bool` |
| Factory | Отвечает за создание сложных объектов | Скрывает конструкцию и инварианты |
| Module | Именованная часть модели | Имя модуля — термин домена |
| Layered Architecture | Изоляция домена от инфраструктуры | Домен не импортирует БД и фреймворки |

## Смежные паттерны

| Паттерн | Суть | Отношение к DDD |
|---|---|---|
| Anemic Domain Model | Мешки с данными, логика в сервисах | Антипаттерн[3] |
| Transaction Script | Логика в процедурах по одной на запрос | Альтернатива для простых доменов[29] |
| Hexagonal Architecture | Порты и адаптеры | Часто лучше слоёв для изоляции домена[1][23] |
| Event Sourcing | Состояние как свёртка событий | Расширяет модель событий[28] |
| CQRS | Раздельные модели записи и чтения | Естественно следует из событий[30] |

## Чек-лист моделирования

**Стратегия**

1. Что здесь ядро, а что — периферия?[7]
2. Где проходят границы контекстов? Кто в них живёт?[1]
3. Как контексты связаны? Какой паттерн на каждой связи?[13][26]
4. Какой язык у каждого контекста? Разные слова — разные значения?[1]

**Тактика**

5. Что здесь сущность (нужна идентичность), а что объект-значение?[1]
6. Где граница агрегата? Что агрегат защищает?[1]
7. Какие правила и где они живут — в объекте или в сервисе?[3]
8. Какие факты важны для экспертов домена? Это и есть события.[1]
9. Нужна ли транзакция шире одного агрегата? Почему?[1]

**Проверка результата**

10. Можно ли сказать, что делает код, не открывая его? (Единый язык.)
11. Есть ли класс, который меняет поля напрямую, обходя правила? (Анемия.)
12. Проходят ли тесты домена без базы данных? (Изоляция.)
