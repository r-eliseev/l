# 11. Репозиторий: доступ к агрегатам на языке домена

*Лист чтения:* 18 минут · **Код:** `ddd_examples/subscriptions/services.py`

> **Краткое содержание.** Репозиторий отдаёт домену готовые агрегаты и прячет от него физическое хранилище, а заодно не даёт SQL превратиться в язык модели.

## Введение

Агрегат — объект с поведением и границей транзакции. Но рано или поздно его нужно получить: показать клиенту подписку, сменить тариф, закрыть месяц. И вот на этом шаге модель чаще всего и ломается.

Самый привычный способ — взять подписку прямо из базы: выбрать колонки, разложить их по атрибутам, собрать объект. Код работает, тесты зелёные. Проблема в другом: он не оставляет домену места. Каждое новое правило — это ещё одна колонка, ещё один джойн, ещё одна ветка в разборе результата. Через полгода SQL-файл становится настоящей моделью, а класс `Subscription` — тонкой обёрткой над строкой.

Репозиторий нужен, чтобы разорвать эту связь. Домен не должен знать, как его хранят; хранилище не должно знать, что значит «активная подписка». Между ними — узкий контракт на языке домена.

## Основной материал

### Что такое репозиторий

Эванс формулирует это так: «For each type of aggregate that needs global access, create a service that can provide the illusion of an in-memory collection of all objects of that aggregate's root type»[1].

Ключевое слово — *illusion*. Репозиторий не обязан быть коллекцией в памяти: внутри может быть SQL, файл или сетевой вызов. Но у вас есть ощущение, что коллекция в памяти есть: вы просите «дай подписку по идентификатору» или «дай подписки клиента» — и получаете объекты, с которыми можно работать как с обычными объектами в памяти.

Отсюда и правило «по одному репозиторию на тип агрегата». У подписок свой, у тарифов — свой, у клиентов — свой. Общий репозиторий «на все таблицы» — это уже не репозиторий, а шлюз к произвольным запросам, и о нём поговорим в ловушках.

### Почему наивные запросы вредны

Цена подхода «просто сделаем SELECT» неочевидна, поэтому её стоит назвать прямо. Эванс перечисляет последствия: техническая сложность доступа к данным забивает код приложения, доменный слой упрощается до нерелевантного, доменная логика уезжает в запросы и в код приложения, а сущности превращаются в контейнеры данных[1].

Последний пункт — самый опасный. Сущность-контейнер не защищает свои инварианты: поле `status` можно поменять напрямую, минуя `pause()`. Fowler описывает результат таких решений отдельным антипаттерном: «The basic symptom of an Anemic Domain Model is that at first blush it looks like the real thing»[3]. Модель выглядит как настоящая, но поведения на объектах почти нет, и вся логика переехала в сервисы[8].

### Что репозиторий возвращает

Репозиторий отдаёт либо полностью сконструированные объекты, либо прокси, скрывающие технологию хранения[1]. На практике это значит: вызвали `get` — получили готовый `Subscription`, с которым можно сразу звать `pause()` и `change_plan()`. Полусобранный агрегат, у которого надо дописать поля вручную, — это не агрегат, а заготовка.

### Границы репозитория

Репозиторий работает с агрегатами, а не с отдельными сущностями внутри агрегата. Достать «строку позиции» или «счёт» изнутри подписки через репозиторий нельзя: наружу торчит только корень. Это не формальность — так границы агрегата превращаются из договорённости в ограничение на уровне кода.

Репозиторий — не для DTO. Ответ для экрана, отчёта или внешнего API — это проекция для чтения, и она собирается отдельно. Смешивать «внутренний доменный объект» и «плоскую структуру для интерфейса» в одном методе — прямой путь к протечкам: рано или поздно поле DTO станет источником правды.

### Сравнение подходов

| Подход | Что вы спрашиваете | Где живёт домен | Чем кончается |
|---|---|---|---|
| Репозиторий | «дай подписку», «дай подписки клиента» | в агрегате | домен не знает про SQL |
| Generic repository | «выполни запрос с параметрами» | в тексте запроса | правила уезжают в запросы |
| DAO | «сохрани строку» | в приложении | инварианты ничем не защищены |
| Query builder | «собери SELECT» | нигде | модель размывается |

### Замена реализации

Контракт репозитория позволяет менять хранилище, не трогая домен: `InMemorySubscriptionRepository` в тестах, реализация поверх SQL в проде, оба — подтипы одного и того же `SubscriptionRepository`. Это же свойство лежит в основе гексагональной архитектуры: «Allow an application to equally be driven by users, programs, automated test or batch scripts»[23].

## Пример в коде

Контракт репозитория в нашем пакете выглядит так (`ddd_examples/subscriptions/services.py`):

```python
class SubscriptionRepository(ABC):
    """Репозиторий даёт доступ к агрегатам на языке домена.

    Evans: «For each type of aggregate that needs global access, create a
    service that can provide the illusion of an in-memory collection of all
    objects of that aggregate's root type».
    """

    @abstractmethod
    def add(self, subscription: Subscription) -> None: ...

    @abstractmethod
    def get(self, subscription_id: SubscriptionId) -> Optional[Subscription]: ...

    @abstractmethod
    def update(self, subscription: Subscription) -> None: ...

    @abstractmethod
    def find_by_customer(self, customer_id: CustomerId) -> Iterable[Subscription]: ...
```

Реализация для примеров и тестов:

```python
class InMemorySubscriptionRepository(SubscriptionRepository):
    """Реализация для примеров и тестов. В проде здесь будет БД."""

    def __init__(self) -> None:
        self._items: dict[SubscriptionId, Subscription] = {}

    def add(self, subscription: Subscription) -> None:
        if subscription.id in self._items:
            raise SubscriptionError(f"Подписка {subscription.id} уже существует")
        self._items[subscription.id] = subscription

    def get(self, subscription_id: SubscriptionId) -> Optional[Subscription]:
        return self._items.get(subscription_id)

    def update(self, subscription: Subscription) -> None:
        if subscription.id not in self._items:
            raise SubscriptionError(f"Подписка {subscription.id} не найдена")
        self._items[subscription.id] = subscription

    def find_by_customer(self, customer_id: CustomerId) -> Iterable[Subscription]:
        return [s for s in self._items.values() if s.customer.id == customer_id]
```

Прикладной уровень работает только с контрактом, не зная реализации:

```python
class SubscriptionApplication:
    """Сценарии: подписаться, сменить тариф, поставить на паузу, отменить."""

    def __init__(
        self,
        repository: SubscriptionRepository,
        publisher: Optional[EventPublisher] = None,
        pricing: Optional[SubscriptionPricing] = None,
        id_generator: Optional[Callable[[], str]] = None,
    ) -> None:
        self._repository = repository
        self._publisher = publisher
        self._pricing = pricing or SubscriptionPricing()
        self._next_id = id_generator or (lambda: f"sub-{id(self._repository)}")
```

А список подписок клиента собирается в проекцию для чтения — отдельный тип, а не словарь (метод `list_for_customer` в `ddd_examples/subscriptions/application.py`):

```python
def list_for_customer(self, customer_id: CustomerId) -> list[SubscriptionView]:
    return [
        SubscriptionView(
            subscription_id=str(s.id),
            customer_id=str(s.customer.id),
            plan_code=s.plan.code,
            status=s.status.value,
            monthly_price=str(s.plan.monthly_price),
        )
        for s in self._repository.find_by_customer(customer_id)
    ]
```

## Разбор примера

**Почему методов ровно четыре.** `add`, `get`, `update` и один поиск по критерию, который понимает эксперт. Репозиторий — не API доступа к данным: это минимальный набор операций, который нужен домену. Всё остальное — либо другой репозиторий, либо проекция для чтения.

**Почему `find_by_customer` возвращает `Iterable[Subscription]`, а не страницу с-total.** Доменный вопрос «покажи подписки этого клиента» не имеет параметра «сколько всего». Всё, что связано с постраничностью, сортировкой и фильтрами, — забота слоя чтения. Если понадобится пагинация, она появится в отдельном read-модели, а не в доменном контракте.

**Почему `get` возвращает `Optional`, а не «пустой агрегат».** Отсутствие подписки и подписка в состоянии «пустая» — разные вещи. Пустой агрегат создаёт соблазн забыть проверку: приложение продолжит работать и упрётся в неожиданный `KeyError` глубоко в сценарии. `None` заставляет спросить: «а что мы делаем, когда подписки нет?»

**Почему `add` и `update` бросают `SubscriptionError`, а не `KeyError`.** Ошибка репозитория — это не сбой системы, а конфликт в терминах домена: «подписка уже существует», «подписка не найдена». Тот же тип ошибок, что и в агрегате, потому что ситуация одна и та же.

**Почему проверка «уже существует» здесь, а не в базе.** Первичный ключ в базе тоже сработает, но сообщит об этом как об ошибке драйвера, а не как о доменной ситуации. Репозиторий отвечает за перевод: он ловит технический конфликт и превращает его в сообщение на языке домена.

**Что даёт замена реализации.** `SubscriptionApplication` принимает `SubscriptionRepository`, а не `InMemorySubscriptionRepository`. Тесты подставляют память, прод — SQL. Ни строчки доменного кода при этом не меняется: контракт один, реализаций сколько угодно.

**Чего в примере нет.** Нет метода `execute_query`. Нет `find_all` с фильтрами в виде словаря. Нет `save()` без указания, что именно сохраняется. Каждое из этих решений выглядит безобидно, но вместе они превращают репозиторий обратно в обёртку над SQL.

## Ловушки

**Generic repository на всё.** `GenericRepository<T>` с методом `find(where: dict)` — самая популярная ловушка. Такой репозиторий не знает ни про агрегаты, ни про единый язык: критерии поиска уезжают в словари, и проверка «а можно ли так делать» возвращается в код приложения. Fowler предупреждает о том же самом: когда бизнес-логика живёт вне сущностей, в сервис-классах[8].

**Репозиторий, отдающий DTO.** Метод `get_summary`, возвращающий словарь с пятью полями, — приглашение писать всю логику по этим словарям. Доменный объект должен возвращаться доменным объектом; проекция для чтения — отдельным типом, как `SubscriptionView` в `ddd_examples/subscriptions/application.py`.

**Репозиторий для членов агрегата.** Отдельный репозиторий «заказов» внутри агрегата «клиента» разрывает границу транзакции: теперь согласованность между ними обеспечивается не кодом, а порядком вызовов.

**`update` без проверки, что объект существует.** Если реализация молча добавляет отсутствующий агрегат, ошибка «подписка не найдена» исчезает, а вместо неё появляется запись в базе без предшествующего чтения — и рассинхрон между состоянием в памяти и состоянием в хранилище.

**Репозиторий без доменных имён.** Метод `get_by_user_id` в домене, где клиент называется клиентом, — это уже не DDD, а переименованный SQL.

Отчёт — это не доменное намерение, а форма отображения. Доменному коду не нужен «отчёт за прошлый квартал по тарифу ritual»: такого понятия в едином языке подписок нет. Скорее всего, «сколько мы заработали на переводе клиентов с light на ritual» — это метрика, и её считает отдельный модуль аналитики, читающий либо свою копию данных, либо поток событий.

Если же отчёт — это не метрика, а регулярная выборка данных для внутреннего экрана, у неё появляется своё место: read-модель со своей формой данных. Fowler описывает это разделение так: «you can use a different model to update information than the model you use to read information»[30], а Azure добавляет, что write- и read-представления часто различаются по природе[31]. Главное — не тащить условия отчёта в доменный контракт репозитория.

## Что дальше

Репозиторий умеет сохранять агрегаты, но не умеет рассказывать, что в них произошло. Пока изменения состояния замечает только вызывающий код, модель остаётся закрытой: остальные части системы узнают о фактах, только если их спросят. Доменные события решают эту задачу — и являются следующей главой.
